ESP-AudioPlayer
System Architecture

A single-chip PCM audio player and Wi-Fi upload target built on ESP32. It streams raw 44.1 kHz / 16-bit stereo from an SD card over I2S, drives a 240x280 ST7789 display through LVGL, and exposes a SoftAP + HTTP upload portal for adding new tracks.

I2S STD 44.1 kHz SPI2 SD / FATFS SPI3 ST7789 SoftAP + HTTP 6 x 4 KB DMA buffers
01

Layered Architecture

Four layers. main.c only wires things together; all behaviour lives in the service and BSP layers.

02

Boot Sequence

app_main() brings up the display first so the user gets immediate feedback while the SD card is probed, then starts the mode controller and the input subsystem.

03

Application Mode State Machine

app_mode.c owns a single volatile app_mode_t. The input task reads it; app_control_task is the only writer that performs heavy transitions.

No return path from PLAYER. Once start_player_mode() succeeds, no command sends the app back to BOOT_MENU. Switching to upload mode after playback requires a reboot.
04

Tasks, Queues and Concurrency

Everything is decoupled through FreeRTOS queues. Only the input task and the LVGL port call into ui.c, always behind lvgl_port_lock().

Backpressure design. The audio path uses a classic free / ready buffer pool. sd_read_task blocks on the free queue, i2s_write_task blocks on the data queue, and the I2S DMA provides the final rate limit.
05

Audio Pipeline

Raw PCM is read from FATFS in 4 KB chunks, scaled in software for volume and mute, then pushed into the I2S DMA.

Wi-Fi Transfer Mode

Upload mode starts a SoftAP on 192.168.4.1 and an HTTP server on port 80. Files are written to a .tmp path first and renamed on success.

07

Cover Art Subsystem

playlist_preload_covers() converts every song.bmp next to a song.pcm into a 140x140 RGB565 LVGL image descriptor backed by PSRAM.

PSRAM budget. Each cover costs 140 x 140 x 2 = 39200 bytes. With MAX_FILES = 128 a fully covered library needs about 4.8 MB of PSRAM held resident for the whole session.
08

Input and Interaction Model

One rotary encoder with a push switch drives the entire UI. Its meaning depends on app_mode_t and, inside player mode, on input_ui_mode_t.

Long-press guard. Short presses arriving within LONG_PRESS_GUARD_US (500 ms) of a long press are suppressed, preventing accidental play/pause when leaving volume mode.

10

Design Notes and Watch Points

  • Task priorities are flat. app_control_task, sd_read_task and input_control_task all run at priority 6, with i2s_write_task at 5. If the SD reader spins on a corrupt card it can starve the I2S writer.
  • Elapsed-time UI updates are rate-limited by a lock timeout. sd_read_task uses lvgl_port_lock(10) and only advances last_elapsed_sec on success, so a busy UI skips a second rather than blocking audio.
  • Pause is implemented as silence, not a stop. The read task keeps pushing zeroed buffers so the I2S DMA never drains. Avoids clicks on resume but burns the buffer pool while paused.
  • Track changes drop in-flight audio. flush_audio_data_queue() returns queued buffers to the free pool instead of draining the DMA, keeping skip latency around one buffer (~23 ms).
  • Wi-Fi is fully deinitialised on exit. esp_wifi_deinit() plus esp_netif_destroy_default_wifi() frees internal RAM for the cover cache.
  • Playlist is built once. Newly uploaded files only appear after a reboot.
  • audio_player_start() is idempotent. The s_initialized guard means queues, DMA buffers and tasks are created only once.
